# Triage

Convert intake into a deterministic Khala work packet or a concrete non-ready
state. Triage is not implementation.

## Use when

- User asks to triage, route, label, clean up, or prepare an issue/PR/request.
- User asks whether an issue is ready for `/workon` or needs information.
- User wants a normalized work request derived from external reporter intake.

## Avoid when

- User asks to fix or implement the issue now; use `/workon` after readiness.
- User asks for code review, CI investigation, or release publishing as the
  primary task.
- The target tracker cannot be accessed and the user requires live forge
  mutation rather than a draft packet.

## Hard rules

- Preserve reporter-authored issues. Do not overwrite the original body; propose
  a linked normalized work request for external intake.
- Ask explicit approval before creating/updating issues, labels, comments, or
  out-of-scope records.
- Any posted triage comment or issue body generated by the agent must start
  with:

```markdown
> _This was generated by AI during triage._
```

## Inputs and outputs

Inputs can be issue/PR URLs, release notes, pasted reports, maintainer requests,
or support-style intake. Outputs are one of:

- `TriageGatewayInput` JSON for the structured-facts step.
- A gateway-derived normalized work packet or split table.
- A non-ready action plan with the matching state label.

## State machine

Apply the route ladder in order:

1. duplicate
2. needs-info
3. out-of-scope
4. split
5. human
6. ready-for-agent

Non-agent pickup states: additional-info-needed, split-needed, ready-for-human,
declined, duplicate. Only ready-for-agent may propose `workon-ready`.

Labels are derived from the gateway label plan; do not paste labels into the
issue body. Preview label setup with:

```sh
khala triage labels ensure --repo <owner/repo> --dry-run
```

## Workflow

1. Gather context: body, comments, labels, reporter activity, related code/docs,
   repo guidelines, duplicates, and prior `.out-of-scope/` decisions.
2. Verify claims before routing when practical. Reproduce bug symptoms or read
   PR diffs/tests; if evidence is insufficient, route needs-info.
3. Produce `TriageGatewayInput` JSON only for the structured-facts step. Do not
   claim route/readiness/labels/publication from prose.
4. Let `buildTriageGatewayResultFromUnknown()` / `normalizeTriageGatewayInput()`
   determine route, validation, issue body, publication plan, and label plan. If
   gateway validation fails, revise the facts or keep the route non-ready; never
   override it with prose.
5. Draft one normalized work packet by default. Propose a split table only when
   scope is clearly too broad for one reviewable PR.
6. Preview publication with:

```sh
khala triage publish --input <packet.json> --dry-run
```

7. Ask for approval before any forge mutation.

## Packet contract

Canonical headings parsed by `/workon`:

- Current behavior
- Desired behavior or Goal
- Acceptance criteria
- Non-goals
- Work Plan
- Risks

Rules:

- Acceptance criteria are plain markdown bullets, never task-list checkboxes.
- `## Work Plan` must contain `### Validation`, `### Documentation`, and
  `### Testing` subsections; put validation, docs, and tests bullets there
  instead of directly under `## Work Plan`.
- Bug packets include behavior/regression validation.
- Triage bodies must include the parseable `khala-triage` metadata comment with
  `schema_version`, `source_kind`, `source_url`, `route_disposition`, and
  `first_matching_rule`.
- `commands/triage-issue-template.md.j2` is the canonical rendering source of
  truth.
- Risks explicitly state breaking-change and review-size risk as low, absent, or
  resolved when applicable.
- Improve-generated or improve-labeled packets include a parser-valid drift
  check using a backtick-wrapped `git diff --stat` or `git diff --name-only`
  command with a concrete baseline ref and `--` followed by concrete in-scope
  paths.

## Progressive disclosure

- Read `AGENT-BRIEF.md` when adapting legacy agent-brief comments or external PR
  triage into the canonical Khala packet.
- Read `OUT-OF-SCOPE.md` before declining an enhancement or updating the
  `.out-of-scope/` knowledge base.

## Failure recovery

- If tracker or code context is unavailable, state the missing evidence and
  route needs-info unless the remaining evidence is enough for a safe packet.
- If the target is a release page or non-issue URL, preserve it as source
  material and draft a maintainer-originated normalized work request.
- If duplicate or out-of-scope evidence is uncertain, ask the maintainer before
  closing, declining, or recording an out-of-scope decision.

## Output

Report triage recommendation, proposed packet or split table, readiness status,
approval question/next action, risks, validation/postflight if mutation
occurred, `Result: success|partial|failed`, and `Confidence: 0..1`.
